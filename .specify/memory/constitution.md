# Pacman Tracker Constitution

## Core Principles

### I. API-First Design

- The backend MUST expose all functionality through well-defined
  REST endpoints (FastAPI) before any React UI consumes it.
- Strava integration MUST be encapsulated behind a dedicated service
  interface so the data source can be swapped or mocked without
  altering consumers.
- Every endpoint MUST have a documented request/response contract
  (OpenAPI auto-generated by FastAPI) kept in sync with implementation.
- React components MUST NOT call external APIs directly; all
  external communication flows through backend services.

**Rationale**: Clean separation enables independent testing of
geo-processing logic, Strava synchronization, and UI rendering.

### II. Test-First Development

- New features MUST have acceptance-level tests written and
  failing before implementation begins (Red-Green-Refactor).
- Street-coverage calculations and geospatial logic MUST have
  unit tests with deterministic sample data.
- Strava API integration MUST be covered by contract tests using
  recorded/stubbed responses so the test suite runs offline.
- Pull requests MUST NOT be merged when any existing test is
  broken.

**Rationale**: Geospatial math and third-party API integration are
error-prone; automated tests are the primary safety net.

### III. Data Privacy by Design

- The application MUST use OAuth 2.0 for Strava authentication
  and MUST NOT store user passwords.
- Access and refresh tokens MUST be stored encrypted at rest.
- The application MUST request only the minimum Strava scopes
  required (activity read).

**Rationale**: Exercise data is personal health-adjacent
information; responsible handling builds user trust and reduces
regulatory risk.

### IV. Simplicity & Incremental Delivery

- Each user story MUST be deliverable and testable independently
  as a vertical slice (UI → API → data).
- No architectural pattern (repository, CQRS, mediator) may be
  introduced unless a concrete, documented problem justifies it.
- Third-party libraries MUST solve a proven need; speculative
  dependencies are prohibited.
- The first milestone MUST be a working map showing a single
  user's covered streets before any gamification features are
  added.

**Rationale**: A focused MVP validates the core value proposition
(street-coverage visualization) before investing in polish.

## Technology Standards

- **Backend**: Python 3.12+, FastAPI, Uvicorn.
- **Frontend**: React 18+ with TypeScript; Vite for bundling.
- **Mapping**: React-Leaflet or deck.gl for interactive street
  maps; Mapbox GL JS acceptable as an alternative.
- **Geospatial**: Shapely and GeoPandas for geometry operations;
  OSMnx for street-network retrieval from OpenStreetMap.
- **Data Store**: PostgreSQL with PostGIS for geospatial queries.
  Docker Compose provides the local development database.
- **CI**: All pushes MUST pass build + test before merge.
- **Code Style**: Backend MUST pass `ruff check` and `ruff format`
  with zero warnings; frontend MUST pass ESLint and Prettier.

## Development Workflow

- All work MUST occur on feature branches; direct commits to
  `main` are prohibited.
- Every pull request MUST include:
  1. A passing test suite.
  2. Updated or new tests covering the change.
  3. A brief description linking to the relevant spec or task.
- Code review by at least one other contributor is REQUIRED
  before merge (single-developer projects: self-review checklist
  in the PR template suffices until a second contributor joins).
- Releases follow semantic versioning; breaking API changes
  MUST increment the major version.
- Backend and frontend repositories (or directories) MUST each
  have independent test suites that can run in isolation.

## Governance

- This constitution supersedes ad-hoc decisions. When a practice
  conflicts with a principle above, the principle prevails.
- Amendments MUST be documented with a version bump, rationale,
  and migration plan for any affected in-flight work.
- Version increments follow semantic versioning:
  - **MAJOR**: Principle removal or redefinition that breaks
    existing workflow assumptions.
  - **MINOR**: New principle or materially expanded guidance.
  - **PATCH**: Clarifications, typo fixes, non-semantic
    refinements.
- Compliance review: each pull request MUST verify adherence to
  the principles listed above. The plan-template "Constitution
  Check" gate enforces this at planning time.
